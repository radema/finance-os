### 2.1 Wave-1 gate — three rounds, not one

The Opus `code-reviewer` gate ran **three times** against this session's work, at increasing
precision, because the first fix round introduced a worse bug than it closed:

1. **First pass** (full diff, `a264462..6a1d8ca`, high intensity, deliberately hunting for
   opus-implementer failure modes since most of that diff was opus-built): found 3 blockers —
   `assemble_rationale` still wrote the P17-forbidden "La tua strategia «…»"; `/allocation` read the
   strategy's *current* version instead of the run's *frozen* one (ADR-0012 violation, reproduced with
   a real 24pp-drift-with-no-run-behind-it example); and `mv_finding` had no resolution concept at all,
   reproduced as a false alarm surviving a cleared drift.
2. **Second pass** (medium intensity, just the fix): B1 and B2 confirmed clean. **B3's fix was wrong** —
   it resolved on `(rule_id, scope_id)` instead of RFC-0008 §4's actual `finding_key` (which hashes in
   `condition.params`), so editing one rule's params while keeping its id made an unrelated *live*
   finding vanish. Also wrong timestamp field (`evaluated_at` instead of `as_of`) and didn't exclude
   `SKIPPED` runs from the candidate set. **This was hiding real findings, which is worse than the
   original over-showing bug.**
3. **Third pass**: all three sub-fixes verified correct via six concrete repro scenarios (table in the
   reviewer's own report). Gate passed. One cosmetic P25 nit found and fixed directly.

**Lesson for next time:** a rewrite of a resolution/ordering predicate against a hash-based key deserves
its own repro-driven check before the first review pass closes it, not just a "does it compile" test.

### 3.1 The B3 regression, for anyone reading only this section

RFC-0008 §4's finding-resolution key is `finding_key = sha256(rule_id ‖ scope_id ‖
canonical(condition.params))`. The first implementation used `(rule_id, scope_id)` alone. If you see
resolution logic anywhere keying on less than the full `finding_key`, that is this exact bug returning —
it silently hides live findings whenever a rule's params change without its id changing.

### 3.2 What to check in the rule-catalog merge before trusting it

The implementer documented these deviations from ADR-L02/ADR-L04's exact specifications, unprompted,
in its own report — none were silently decided, but none were reviewed either:

- **`bucket_below_target_value`**: the ADR's params sketch is a nested `target: Money`; the implementer
  flattened it to `target_amount`/`target_currency` because `LeafCondition.params` is a flat
  `Mapping[str, str]` with no nested-object slot. Plausible mechanical necessity — confirm the flattening
  didn't lose the `target.amount > 0` guard ADR-L02 §4.4 requires.
- **`untargeted_allocation`**: added an `asset_class` param not in RFC-0007 §4.2's stated
  `(scope, threshold_weight)` signature, reasoning that the fixture math needs to select which
  untargeted class. Check whether this is a genuine gap in the RFC or a misread of how the kind is
  supposed to be parameterized per-class already (e.g. via `scope`).
- **`allocation_absent`** reuses `FACT_DRIFT` rather than declaring the new `targets`/`allocation` facts
  ADR-L02 §4.3 names. The implementer's reasoning: `DriftLine` already carries `current_weight` and
  `effective_target` for every targeted leaf, including unallocated ones, so a new fact would be
  redundant. Check this against ADR-L02 §4.3 point 3, which specifically warns against deriving
  `effective_band`-adjacent values outside the kind's declared facts — confirm reusing `FACT_DRIFT`
  doesn't quietly reintroduce that.
- **Invented `FactSet` fields** not in either ADR: `FACT_ALLOCATION` (per-class), `FACT_RESIDUAL`,
  `FACT_BUCKET_VALUE` (scope-level total), `asset_labels` (for `over_apportioned`'s P16 instrument
  naming). None of these were specified, all were added to make the kinds buildable. Check each against
  RFC-0006 §3.1's no-computation boundary — a new fact should carry data the Strategy/Portfolio Engine
  already computed, not something the Rule Engine derives itself.
- **`evaluate_strategy` wiring**: only portfolio-scoped runs populate the apportionment fact ("I-9 is
  portfolio-wide, `over_apportioned` only meaningfully authored there" — check this against ADR-L04's
  own text, which doesn't explicitly restrict the kind to portfolio scope).
- **The "unresolvable apportionment → `SKIPPED(missing_fact)`" path** (ADR-L04 §4.3, "never invent a
  partial denominator") is implemented but **unreachable** — the implementer's minimal
  `compute_apportionment` has no failing external dependency that could trigger it. Latent, not tested
  by construction. Needs either a forced-failure test or an honest note that it's unverified.
- **`over_apportioned`'s anchor**: implementer reports the firing range as open `(1, 2]`, with `1.00`
  a limit never attained on a `FIRED` row (an asset leaves the affected set exactly at `A == H`, per the
  strict `gt` predicate). This reads as *consistent* with ADR-L04 §4.3's "empty affected set → NOT_FIRED,
  severity=None" rather than a deviation — but confirm the dedicated test actually exercises the boundary
  rather than just asserting the open-interval claim in prose.

None of these looked wrong on inspection, and gates were green throughout, but "gates green" doesn't
verify formula fidelity to a spec this precise — that needs the Opus pass this session didn't get to.
