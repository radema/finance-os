### 3.2 ADR-L04 — `over_apportioned` severity (closes O3)

`severity = 1 + Σdeficit / Σapportioned` = `2 − coverage`, aggregated over affected assets: **1.00
exactly at the firing threshold**, 2.00 when the position is fully sold out, range `(1,2]`, total,
expressible in the existing step algebra with no bound literal.

O3's naive `1 + deficit/holding` was rejected **on a defect, not on taste**: it keeps ADR-0025's
denominator, which is **zero in the commonest firing state** (a full exit) — and a zero denominator
does not yield a null severity, it raises `SkipSignal(ZERO_DENOMINATOR)` (`rule_engine.py:466`), so
the finding would vanish into run health instead of firing.

**Fixture consequence:** UX-0001 §8.5 row 9 severity `0.15` → **`1.13`** (stored `1.13207547`), and
**row order moves** — `over_apportioned` 9→8, `drift GOV_EUR·Pension` (1.05) 8→9. All three `ORDER BY`
clauses stay exercised. The synthetic ordering test owed two additions (priority dominance at a tiny
margin; a null sorting below `1.00`) — **both landed in W1c.**

  Hypothesis** — a time-budget decision, and a legitimate thing to strengthen later.

### A note on process that cost real time

Three agents died on stream watchdogs (600s no-progress) and one on an API drop. The recoverable
pattern: **`SendMessage` to the same agent resumes it from its transcript with context intact** — far
cheaper than re-dispatching. The avoidable cause: an agent held a long-running search in the
foreground while "working on something else". Dispatch prompts should say: run long jobs in the
background, and **commit after each deliverable, not once at the end** — uncommitted work in a
worktree is lost work when the stream dies.
