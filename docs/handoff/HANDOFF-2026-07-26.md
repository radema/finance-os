  Engine entry points the plumbing layer wires:
  ```
  portfolio_engine.compute_holdings(operations, *, as_of, accounts=None) -> tuple[Holding, ...]
  portfolio_engine.compute_allocation(holdings, assets, prices, *, scope, as_of, currency)
  strategy_engine.compute_drift(allocation, targets, *, strategy_version_id) -> DriftComputation
  rule_engine.evaluate(rules, facts, *, registry=REGISTRY) -> tuple[RuleFiring, ...]
  rule_engine.replay_trace(trace) -> ReplayResult | None
  decision_engine.materialize(firings, strategy_version, run, *, next_id, recorded_at)
  ```

  **The replay property test is the session's most load-bearing outcome, and it earned its keep.**
  `replay_trace` reads only binding names/values, step operands and recorded skip evidence — never
  `outcome`, never `skip_reason`, never a source. Hypothesis generates whole evaluations (trees to
  depth 2, both tolerance kinds, on-target and breached, unpriced assets, untargeted classes, stale
  facts, empty portfolios, unknown kinds) and asserts `replay(blinded(trace)) == (outcome, skip_reason)`,
  where **blinded** means every `SourceRef` is overwritten with a poison value and every `observed_at`
  dropped — so a replay leaning on provenance fails. Tampering a step or binding, deleting a consumed
  binding, or a non-boolean final step all raise; a FIRED trace with no steps replays to `None` and can
  never pass. Non-vacuity is measured, not assumed (per 400 examples: FIRED 41 · NOT_FIRED 32 ·
  missing_fact 222 · stale_fact 27 · zero_portfolio_value 18 · ERROR 201). It generates programs over
  the whole 15-op algebra, so the V1.0 kinds using `ratio_to`/`add` are already replay-safe.

  **It found two genuine defects rather than confirming a comfortable assumption:** a family-level skip
  whose reason was not reconstructable from its own trace, and `divide_safe`/`ratio_to` raising on a
  large ratio, violating RFC-0006 §4.1's totality requirement. Both fixed and covered.

### 2.2 ADR-L01 — Operation link-flag truth table

Closes RFC-0011 §8.3. **`transfer_pair_id` is mutually exclusive with both `corrects_id` and
`cash_leg_of`; `corrects_id` and `cash_leg_of` combine freely.** Five of eight combinations legal:
primary economic row, auto-emitted cash leg, transfer side, correction primary, and the correction's
cash side (where `corrects_id` → the original leg and `cash_leg_of` → the sibling correction primary;
this row is *mandatory* whenever the corrected row has a leg).

A CORRECTION never carries a pair id — pairing is derived via `corrects_id → target.transfer_pair_id`.
That preserves the exactly-two-rows / one-IN / one-OUT / nets-to-zero invariant which keeps ADR-0028's
transfer integrity a one-query check. A CORRECTION of a transfer pair is two CORRECTION rows with
equal-and-opposite deltas and NULL pair id on both. A CORRECTION of a legged operation is always
written as a primary+leg pair even when one delta is zero, so the writer has one code path.

Adopts **UX-0001 §7.1 Option 1**: cash legs keep the parent's `type`, and the sign checks gain a
cash-leg exemption exactly as `CORRECTION` is already exempt. This keeps the seven-value enum, so no
further product ratification is needed. The truth table is invariant under all three of UX-0001's
options — only the `type` value and the exemptions change.

### 2.3 ADR-L02 — Severity declarations

Required because RFC-0006 §12's registry completeness test **fails the build** unless every kind
declares a severity formula or an explicit `null`.

| Kind | Severity | Reasoning |
|---|---|---|
| `unassigned_residual_above` | `residual_weight / threshold_weight` | Follows UX-0001 §7.2; reproduces fixture row 10's 1.22 exactly. No `abs()` — deficits stay owned by `over_apportioned` |
| `allocation_absent` | **`null`** | Absence is binary. The only commensurable denominator (`effective_band`) is optional per ADR-0017, so any formula would be partial; the magnitude is already reported commensurably by `drift_outside_tolerance` (RFC-0007 §4.1). A `1.0` constant is an arbitrary position dressed as a measurement |
| `bucket_below_target_value` | `1 + shortfall/target` = `2 − coverage` | 1.00 at target, 1.50 at half covered, 2.00 when empty. Total, monotonic, algebra-expressible, correctly anchored. Emergency reads **1.25** against the fixture |

Also generalizes RFC-0006 §11's severity test to: **`severity == 1` at each kind's own firing threshold.**

### 3.4 DuckDB engine limits discovered while writing 001

These are engine constraints, not design choices, and each pushes an invariant from the DDL into the
application layer — which raises the stakes on the property tests that guard them.

| # | Limit | Consequence |
|---|---|---|
| E-1 | **DuckDB 1.5.5 does not support `ALTER TABLE … ADD CONSTRAINT/FOREIGN KEY`** (`Not implemented Error`) | ERR-8's plan of adding `strategy.current_version_id`'s FK after `strategy_version` exists is unimplementable. The column is a plain `VARCHAR`, repository-enforced — the same posture already accepted for `alert.rule_id` / `recommendation.rule_id` under ADR-0027 |
| E-2 | **Inline CHECK constraints are anonymous** — DuckDB raises a generic `ConstraintException` with no per-constraint name | The paired-Operation writer cannot tell *which* rule fired from the exception type, only from message text. Therefore the writer must construct rows correctly up front rather than probing by catching failures |

Additional notes for whoever writes the repositories:

- **Do not add a `Σ bucket_apportionment.quantity ≤ Holding` CHECK.** ADR-0025 deliberately made that
  an evaluation-time finding (`over_apportioned`), not a write-time invariant. Only `quantity >= 0` is
  enforced in the DDL.
- **Ten invariants (W1–W10) are repository-enforced, not DDL-enforced**, and each needs a named
  property test before the first non-BUY write: leg totality, leg shape/amount formula, no leg-of-a-leg,
  transfer-pair cardinality and nets-to-zero, no correction chains, correction-pair totality (cash and
  transfer), correction leg amount, atomicity (one transaction, one `import_batch_id`), and append-only.
  W10 is the one that most needs CI contract **C6**, since DuckDB has no per-table grants.

### 3.6 Core-implementation divergences from the RFCs' literal text

Each is documented in-code. None changes an invariant; several were forced by a contradiction.

| # | Divergence | Why |
|---|---|---|
| C-1 | `AssetClass`, `Priority`, `SuggestionClass`, `Outcome`, `SkipReason` live in `core/shared`, not their nominal owning contexts (RFC-0004 §4.1) | They cross contexts, so contract **C3 is literally unsatisfiable** otherwise. Ownership stays a documentation statement |
| C-2 | `FactSet.drift` carries `Bound[DriftLine]` (all eight bindings + tolerance), not RFC-0006 §4's sketched `Bound[Decimal]` | RFC-0007 §4 mandates eight bindings per leaf. The kind binds them and recomputes `drift` as an explicit **step**, matching RFC-0009 §4.1's own example — which is what makes the intermediate computation visible in the trace, as §8.3's done-when requires |
| C-3 | All bindings of one fact share the fact's derived `SourceRef`, narrowed by `path` — not RFC-0009's illustrative per-binding sources | The "target with no holding → `current_weight` 0" edge case belongs to the engine that owns it. Stage-B resolvability is preserved |
| C-4 | `evaluate` returns one sequence of `RuleFiring` (each carrying its trace), not `(firings, traces)` | Matches RFC-0004 §4.1's own payload; parallel lists would duplicate the trace |
| C-5 | Step operand field is `inputs`, not RFC-0009's `in` | `in` is a Python keyword; an alias at the persistence boundary is a permanent footgun |
| C-6 | Skip evidence carries its reason: `unavailable_facts: (name, reason)[]` | Generalizes RFC-0006 §5's "trace lists which" so the reason is reconstructable — this is one of the two defects the replay test caught |
| C-7 | Leaf nodes must declare a `Tolerance` | A target with no band cannot yield `effective_band`. Interior tolerances are stored but unused until V1.1 |
| C-8 | `severity = None` when `effective_band == 0` (a RELATIVE band on a zero target) | Undefined, not infinite. ERR-1 already permits a null severity |

**Invented, and flagged for ratification:** `RiskLevel` members (CONSERVATIVE / MODERATE / BALANCED /
GROWTH / AGGRESSIVE). The corpus calls for an ordinal enum and names no members.

**Two follow-ups this creates:**

- **`StrategyVersion` has no `version_number`** (ERR-8's DDL has none), so the assembled rationale cites
  the freeze date rather than "v3". Any UI showing "v3" must derive it by walking `parent_version_id`.
- **`asset_class_label` is a mechanical `EQUITY_DEVELOPED → Equity/Developed` default.** ADR-L03 §5.2
  wants a real label registry; `FactSet.labels` lets a caller override it for observations, but the
  assembled rationale still uses the mechanical form because ADR-0023 forbids reaching outside the
  frozen version. One inconsistency to close when the label registry lands.

### 3.7 Design-detector waiver (one, deliberate)

`.impeccable/config.json` carries a single `detector.ignoreValues` entry: rule **`side-tab`**, scoped to
`src/financeos/web/static/css/components.css` only.

The detector flagged `border-inline-end/start: 6px solid var(--seal)` on `.rail-gauge__clamp--start/--end`
as a "thick coloured border on one side of a card". It is not: those rules sit on a `width: 0; height: 0`
box with `border-block: 6px solid transparent`, which is the standard CSS-triangle technique rendering a
**caret**. They implement UX-0001 §4.1's requirement that the tolerance rail clamps with a caret when
severity overflows ±3 band-widths, and the caret is drawn in CSS rather than typed because `◀` falls
outside the vendored Latin subset and Local First forbids widening the font for one glyph.

Scope is deliberately narrow: every other detector rule stays active on that file, and `side-tab` stays
active everywhere else in the project. Test before reinstating: zero dimensions + transparent borders on
the perpendicular axis means a drawn glyph and should stay; a thick accent border on a card with real
dimensions is a genuine finding.

#### Wiring contract for W1c (from the core implementer — do not rediscover this)

`evaluate_strategy` composes in this order:

> load `sv` **once** → `compute_holdings` (for Bucket scope, resolve `VirtualHolding`s and call
> `.as_holding()`; the engine takes `Sequence[Holding]` and does not branch on scope) →
> `compute_allocation` → `compute_drift(allocation, sv.targets, strategy_version_id=sv.id)` → build
> `FactSet` → compute `input_digest` → construct `EvaluationRun` → `evaluate(sv.rules, facts)` →
> `materialize(...)`

- **`FactSet` assembly is two lines**, and the second one is the important one:
  `FactSet(as_of=…, scope=…, unavailable={"drift": comp.unavailable} if comp.unavailable else {}, …)`.
  **Never invent a partial denominator.** If `comp.unavailable` is set, pass it — that is exactly what
  turns an unevaluable rule into `SKIPPED(<reason>)` instead of a reassuring `NOT_FIRED`, which ADR-0016
  identifies as the failure mode most likely to mislead.
- **`materialize` takes `next_id` (IdGen) and `recorded_at` (Clock) as values** — engines hold no ports
  (I-7). It raises `RuleNotInVersionError` when a firing's rule is absent from the pinned version
  (ADR-0027's replacement for the dropped FK) and `TemplateRenderError` when a message references a
  binding the trace lacks — so validate templates against the kind's binding namespace at freeze time.
- **`input_digest` must be 64-char lowercase sha256**, so assemble facts *before* constructing the run.
  Use `core.shared.canonical_json` + `sha256_hex` over `(condition, bound values, as_of)`, excluding
  sources and `observed_at` (RFC-0006 §10 rule 5).
- **`engine_versions`**: `{m.ENGINE_NAME: m.ENGINE_VERSION for m in (portfolio_engine, strategy_engine, rule_engine, decision_engine)}`.
- **Repository mapping**: `Recommendation` keeps `run_id`/`strategy_version_id`/`rule_id`/`input_refs`
  inside `Provenance` — flatten to migration 001's columns. `Operation` carries scalar `price`/`fees` +
  one `currency` (no `Money` fields), matching the DDL 1:1. Prices reach the engine as `PriceView`, one
  per asset, already ASOF-resolved by the query layer.
- **Staleness** is measured against `facts.as_of` (no clock in core). Drift facts currently carry
  `observed_at=None`, so nothing goes stale in the skeleton; when the real price provider lands, set
  `observed_at` from `PriceView.valid_date` and the `stale_fact` path activates with no engine change.
- **Still unbuilt, by design:** combinators, the other five condition kinds, `over_apportioned`,
  `heterogeneous_strategies` (needs a `SkipReason` member when portfolio-scope evaluation arrives), and
  the W1–W10 cross-row invariants (repository-enforced per ADR-L01).

## 5. THE OPEN DECISION — pick a visual world

**This gates every remaining Wave 1 screen.** Three worlds were built as offline proofs after the first
identity was rejected (P12). Each shows both colour schemes, the tolerance rail in *and* out of
tolerance, all four outcome chips, trace-ladder rows, and one real ECharts chart with the fixture's five
asset classes.

```
docs/design/worlds/a-calcolatrice.html
docs/design/worlds/b-vetro-sommerso.html
docs/design/worlds/c-mosaico.html
```

Regenerate with `uv run python docs/design/worlds/build_proofs.py`.

| | World | Reference | Strength | Chart language | Elevation |
|---|---|---|---|---|---|
| **A** | La Calcolatrice | Olivetti / Pintori; flat poster inks on warm near-white; Archivo + Martian Mono | Strongest chrome voice, most conventional chart | Flat hard-edged blocks; target as a heavy ink rule on the same axis | None |
| **B** | Vetro Sommerso | Murano, dark-first; deep ink-blue ground; translucent cased canes with a luminous leading edge | Strongest atmosphere; least like any finance dashboard | Submerged layers — but the idea only half pays off on a plain bar; it wants the nested allocation tree | One named luminous-edge level, tokenised per theme |
| **C** | Il Mosaico | Ravenna tesserae; warm bone ground | **Strongest chart form by a distance** | Every quantity drawn as **countable discrete units** separated by grout | None — grout gaps carry separation |

**The implementer recommends C · Il Mosaico**, and the argument is sound: the original complaint was that
the data visualisation had no identity, and C is the only world where the *mark* carries the identity
rather than the palette — swap the hues out and it is still unmistakably this product. It is also not
arbitrary decoration: this domain's numbers genuinely are sums of countable things (units apportioned
across Buckets, evaluations in a run, band-widths of drift), so letting the reader count rather than
compare lengths is the honest picture of a whole that must reconcile to net worth. A and B would both
remain "a bar chart with nicer colours".

**Cross-graft on offer:** C's tesserae chart language with A's typography (Archivo + Martian Mono), since
C's chrome is its weakest part and A's is its strongest.

### 5.1 The structural fix, present in all three

**One reserved alarm hue, excluded from the series set.** There is one palette with one hue held back, so
a status colour can never impersonate a datum and the chrome/series pair cannot drift apart again — which
is exactly how the rejected world failed. In World A, in-tolerance is additionally *neutral* rather than
green, on the reasoning that the system reports rather than congratulates.

### 5.2 A caveat that reframes the original complaint

The dataviz accessibility gates pin every series hue into **OKLCH L 0.43–0.77 with chroma ≥ 0.10** (a
narrower band in dark). Attempts at deep saturated poster inks all *failed* the lightness band. So **no
accessible 5-hue categorical set can be dark-and-inky**, and all three palettes necessarily sit at
mid-lightness and mid-saturation.

This is why hue alone could never have delivered the identity, and why the implementer pushed **form,
ground and type** instead. If more chromatic drama is wanted, the honest levers are the **ground** and the
**mark** — not the series hues — or a consciously accepted CVD warn on specific pairs. Every palette was
solved by search over hue order × lightness ladder × chroma against the validator in both schemes; no hex
was hand-picked. B carries a 7.6 protan warn (6–8 band), legal only with the secondary encoding it ships.

### 5.3 What the choice invalidates, and what it does not

**Rewritten for the winner:** `DESIGN.md` and `.impeccable/design.json` (both currently describe the
rejected world), and the token values in `src/financeos/web/static/css/*.css`. Unused `woff2` files get
deleted once the faces settle. `DESIGN.md` must be complete enough to adjudicate literal-vs-token drift,
or the `design-system-color` rule will keep reporting false drift (§3.7's root cause).

**Unaffected by the choice:** `PRODUCT.md` (current and correct — keep it), the five component-contract
partials, the preview harness, the fixture module, `base.html`, the ECharts helper pattern, and the
vendored assets.
